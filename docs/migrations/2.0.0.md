# Upgrading to 2.0.0

2.0.0 has six breaking changes. Most apps only need the version bumps in section 1 and the Sentry section; the rest
applies only if you use the API it names.

| Change                                                                          | Affects                                                    |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| [Raised peer and Node floors](#1-raise-the-peer-and-node-floors)                | everyone                                                   |
| [`trustCloudFrontIPs` removed](#2-trustcloudfrontips-is-replaced-by-trustproxy) | apps passing `trustCloudFrontIPs` or relying on CloudFront |
| [Sentry 11](#3-sentry-11)                                                       | everyone using `@signmax/remix-base/instrumentation`       |
| [msw 3 in `test/helpers`](#4-test-helpers-require-msw-3)                        | test suites importing `@signmax/remix-base/test/helpers`   |

## Do I need to do anything beyond section 1?

Run from the repository root. No output from a command means its section does not apply.

```sh
# section 2
git grep -n 'trustCloudFrontIPs'
# section 3: options init no longer accepts
git grep -nE 'maxIncomingRequestBodySize|trackIncomingRequestsAsSessions|ignoreIncomingRequestBody|dropSpansForIncomingRequestStatusCodes|incomingRequestSpanHook|enableLogs|sendDefaultPii'
# section 3: your own Sentry setup
git grep -nE 'wrapServerLoader|wrapServerAction|sentryHandleRequest|sentryReactRouter|sentryOnBuildEnd|beforeSendTransaction|ignoreTransactions|tracesSampler|ignoreSpans'
# section 4
git grep -nE 'gqlOpHandler|onUnhandledRequest|StrictResponse|from "msw"'
```

## 1. Raise the peer and Node floors

| Package                                          | 1.1.0       | 2.0.0      |
| ------------------------------------------------ | ----------- | ---------- |
| Node (`engines.node`)                            | `>=22.22.0` | `>=26.0.0` |
| `react-router`, `@react-router/express`          | `^8.3.0`    | `^8.5.1`   |
| `express`                                        | `^5.2.1`    | `^5.3.0`   |
| `@sentry/react-router`, `@sentry/profiling-node` | `^10.70.0`  | `^11.11.0` |
| `msw` (new, optional)                            | —           | `^3.0.4`   |

`express` 5.3.0 is required for `proxy-addr` 2.0.8 (CVE-2026-90711: a `trust proxy` subnet with zero leading bits, such
as `::ffff:10.0.0.0/8`, trusted every client and let it set `req.ip`) and the `qs` 6.16 CVE fixes. Raise these ranges in
the pnpm catalog in the same change as `@signmax/remix-base` itself and run `pnpm install`.

pnpm does not enforce `engines` on install, so check your Dockerfile, CI `node-version` and devcontainer run Node 26.

## 2. `trustCloudFrontIPs` is replaced by `trustProxy`

`serveApp` no longer fetches CloudFront IP ranges. Proxy trust is a static list applied once at startup:

```ts
trustProxy?: string[] | false // default ["loopback", "linklocal", "uniquelocal"]
```

| 1.1.0                       | 2.0.0                                                  |
| --------------------------- | ------------------------------------------------------ |
| `trustCloudFrontIPs: true`  | remove it (the default list applies)                   |
| `trustCloudFrontIPs: false` | `trustProxy: false`                                    |
| option unset                | unchanged, but CloudFront ranges are no longer trusted |

TypeScript rejects a leftover `trustCloudFrontIPs`. In plain JavaScript it is silently ignored, so a leftover
`trustCloudFrontIPs: false` turns proxy trust **on** with the default list.

The default fits traffic arriving through an in-cluster proxy with a private address (Envoy in `10.244.0.0/16`):
`req.ip`, `req.protocol`, the Sentry user IP and the `serverContext` IP all come from `X-Forwarded-*`. If a host still
receives requests directly from CloudFront or another public proxy, `req.ip` is now that proxy's address. Pass its
ranges explicitly, written in plain IPv4 notation:

```ts
await serveApp(build, { trustProxy: ["loopback", "linklocal", "uniquelocal", "203.0.113.0/24"] })
```

## 3. Sentry 11

`init` from `@signmax/remix-base/instrumentation` already absorbs the v11 changes to its own options: `enableLogs` is
gone (the pino integration enables logs), the HTTP integration uses `maxRequestBodySize: "none"`, request bodies stay
out of the broader v11 `dataCollection` defaults, and the health-check `tracesSampler` matches on `url.path`. Your code
needs changes in three places.

### 3.1 Options passed to `init`

`init` spreads your options over its defaults and type-checks them against v11:

- `httpIntegration` overrides use the consolidated v11 names. `tsc` reports the old ones.

  | v10                                      | v11                                     |
  | ---------------------------------------- | --------------------------------------- |
  | `maxIncomingRequestBodySize`             | `maxRequestBodySize`                    |
  | `ignoreIncomingRequestBody`              | `ignoreRequestBody`                     |
  | `trackIncomingRequestsAsSessions`        | `sessions`                              |
  | `incomingRequestSpanHook`                | `onSpanCreated`                         |
  | `dropSpansForIncomingRequestStatusCodes` | `ignoreStatusCodes` (deprecated in v11) |

- Remove `enableLogs` and `sendDefaultPii`; both options were removed.
- A `tracesSampler` or `ignoreSpans` you pass that matches on span **names** stops matching without an error: both run
  when a span starts, before Express resolves the route, so an incoming request span is named just `GET`. Match on
  attributes instead, e.g. `samplingContext.attributes["url.path"]`. A `tracesSampler` you pass replaces the built-in
  health-check filter.
- `beforeSendTransaction` and `ignoreTransactions` no longer run, because spans are streamed. Move filtering to
  `ignoreSpans` and scrubbing to `beforeSendSpan`.

### 3.2 Your own `@sentry/react-router` setup

These are in your app, not in this package. Follow the
[Sentry v10 → v11 migration guide](https://github.com/getsentry/sentry-javascript/blob/develop/MIGRATION.md) for
anything not listed; the items most React Router apps hit:

- The Vite plugin moved: import `sentryReactRouter` (in `vite.config.ts`) and `sentryOnBuildEnd` (in
  `react-router.config.ts`) from `@sentry/react-router/vite`.
- Loader and action spans now come from React Router's instrumentation API. Export
  `instrumentations = [Sentry.createSentryServerInstrumentation()]` from `entry.server.tsx`. `wrapServerLoader`,
  `wrapServerAction` and `sentryHandleRequest` were removed; use `wrapSentryHandleRequest`.
- A client-side `Sentry.init` without `dataCollection` now collects user info, cookies, headers and request/response
  bodies by default. Set `dataCollection` explicitly if that is not wanted.
- Set searchable per-request values with `Sentry.setAttribute(s)` as well as `setTag(s)`: scope tags still reach errors
  but no longer reach spans. `sentryScopeMiddleware` already sets both.

### 3.3 What changes in Sentry itself

No code change, but expect it after deploying:

- Span attributes and ops were renamed (`http.method` → `http.request.method`, `http.status_code` →
  `http.response.status_code`, `middleware.express` → `middleware`, React Router loader/action ops → `function`). Update
  dashboards, alerts and dynamic sampling rules keyed on the old names.
- `attachStacktrace` defaults to `true`: `captureMessage` events carry a stack trace, which can open new issue groups
  and mark sessions as errored.
- Errors that reach Express' error handling with a 5xx status are captured automatically. With `serveApp`, that is
  errors from your own `middleware`/`preMiddleware` and failures of the React Router handler itself (the adapter passes
  them to `next(error)`). Errors from loaders and actions are handled by React Router and still reported through your
  `handleError`.

## 4. Test helpers require msw 3

`@signmax/remix-base/test/helpers` imports `msw` from your project, which now has to be msw 3 (declared as an optional
peer, `^3.0.4`). `gqlOpHandler`'s `handler` parameter changed type from msw 2's `StrictResponse<JsonBodyType>` to msw
3's `HttpResponse<JsonBodyType>`; calls passing `HttpResponse.json(...)` need no change.

For your own msw usage, the changes most test suites hit (full list in the
[msw 3.0.0 release notes](https://github.com/mswjs/msw/releases/tag/v3.0.0)):

- `server.listen({ onUnhandledRequest })` is now `onUnhandledFrame`. vitest does not type-check, so the old name passes
  `vitest` and only fails `tsc`.
- msw no longer manages cookies in Node: `request.headers.get("cookie")` is `null` in handlers; use the `cookies`
  resolver argument.
- msw is ESM-only, `graphql` handlers moved to `msw/graphql`, and fake timers are no longer bypassed, so advance them
  for delayed responses.
